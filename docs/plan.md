# NodeDance 分阶段开发与审查计划

## 基线与执行规则

产品基线为 CST-Cat/NodeDance，默认 Core 地址 `127.0.0.1:8180`，API 使用 `/api/v1`，Agent 使用 `/ws/v1`。所有工作始终直接在 `main` 上进行，不创建任何其他分支。

Luna Work 是唯一代码修改者。一个大阶段完成后再提交审查。独立审查者只核对当前阶段实际变更、调用路径和必要构建结果；发现明确错误时，按文件、位置、原因、修正动作和复验范围驳回给同一 Luna Work 会话。审查者不修改代码，不以覆盖率、旧验收记录、非本阶段功能或缺少 VPS 为由驳回。

审查结论只有：

- **PASS**：阶段目标和当前阶段的必要检查均完成。
- **REJECT**：有可定位的编译错误、重复实现、需求偏离、权限绕过、数据损坏或危险操作。
- **WAIT_FOR_VPS**：MVP 本地源码交付完成，只等待用户安排真实 VPS 联调。

没有明确证据的问题不得阻止进入下一阶段。重复公共机制一旦指定归一，必须只剩一条可运行实现。开发期旧数据库和历史开发数据不做 schema/data 迁移，可删除后由当前 schema 重新初始化；运行中的当前 schema 数据不得在正常启动时重置。禁止重建旧验收系统或同等作用的新平台。构建错误、权限绕过、数据损坏和 Docker 误操作阻止验收。修复后只复验受影响路径。

开发顺序：阶段 0 清理与基础架构统一 → 阶段 1 MVP → 用户提供 VPS 后进行一轮真实联调 → 阶段 2 至阶段 7 顺序交付。不得等待 VPS 才开始或完成本地可做的 MVP 源码。

## 阶段 0：清理与基础架构统一

以现有源码为基础整理，不重写项目。

1. 删除旧 `docs/stages/`、`docs/reviews/`、`reports/`、旧需求追踪和测试夹具；用本计划替换旧计划，更新架构说明与 README。删除 S00–S17、旧验收报告、已不存在脚本和阶段专用 Playwright 命令。
2. 保留 `.tool-versions` 与 `web/pnpm-lock.yaml`、Go module files。删除重复 Node 版本文件、内部 pnpm 安装器、工具链锁文件和旧工具检查/安装脚本。Makefile 只保留依赖安装、类型检查、构建、运行和基本测试入口；Vite 使用通用开发代理配置。
3. 删除 Agent 自动更新、发布打包与监督代码、Core 更新任务和 Web 更新界面，保留 Agent 手动运行、安装及 systemd 管理。
4. Core 仅保留 `internal/core/tasks/` 作为通用远程任务状态库。Compose 项目存储仅管理项目清单；Compose、文件模块不保留独立通用状态账本。SQLite 仅初始化当前完整 schema，不保留 schema 版本号、历史迁移 SQL 或旧 schema/data 兼容迁移；旧开发库可删除。阶段 2 的历史监控图表是现行产品功能，须正常存储和查询。
5. Agent 仅保留 `internal/agent/taskjournal/` 作为持久通用任务日志，并让 `taskrunner` 负责统一执行和结果上报。文件事务或容器重建所需的短期恢复记录只能保留为业务恢复数据。
6. 只由 `internal/agent/docker/engine.go` 创建 Docker SDK Client、解析本地 Socket 并协商 API 版本。操作、日志统计、镜像、Compose 和重建复用这个 Client。每类流保留合适的 Context、响应头超时和关闭策略；Docker 不可用时主机监控继续工作。
7. `web/src/api.ts` 是唯一普通 HTTP 请求实现，统一 Cookie、CSRF、超时、错误和登录失效；业务 API 文件只保留业务方法。`streamApi.ts` 独立处理 WebSocket。

**一次基础检查**：前端类型检查和构建成功，Core 与 Agent 编译成功；无失效引用、空路由、重复通用任务日志、多个 Docker Client 生命周期或多份 HTTP 请求实现；无新旧验收平台；工作仍在 `main`。不需要 VPS 或多版本矩阵。通过后立即进入阶段 1。

## 阶段 1：MVP

交付单管理员登录、真实 Core-Agent WSS 通信、多 VPS 首页、主机监控、Docker 全量发现和容器启停。

- Core：启动入口支持监听地址和数据目录；保留 Session、CSRF、Origin、安全 Cookie、单管理员首次设置/登录/登出、Agent 身份、必要 SQLite 表和嵌入式 Web 资源。
- Agent：注册与设备凭据验证、WSS 重连和心跳、CPU/内存/磁盘/网络/运行时间采集。Docker 不存在或无权限不得停止主机监控；断线后旧状态不得显示为当前状态。
- Docker：全量扫描、Events 和周期校验，发现独立与 Compose 容器；显示真实名称、镜像、状态、健康、时间、宿主机 IP 和端口协议；真实启停重启经过统一 Core Task、Agent Runner 并核实结果。
- Web：未登录只显示管理员形象和登录入口；登录后首页同时显示多台 VPS 卡片及对应 Docker 信息。操作必须访问真实 API，不得用静态数据或即时“成功”伪装。

VPS 提供前，本地完成前端检查、Go 编译、Core 初始化/登录/退出和未登录拒绝验证、本地 Agent 指标链路、Docker 不可用状态。若本机存在可安全使用的 Engine，可用独立容器验证发现和启停；否则记录未验证项。不要求真实多 VPS、Docker 版本矩阵或复杂模拟环境。源码达到条件后返回 **WAIT_FOR_VPS**。

用户主动提供 VPS 后进行一轮联调：部署 Core、安装 Agent、验证注册/连接/重连、读取现有容器、用专用测试容器执行并从 Docker CLI 核对操作，确认断线状态与恢复，清理本次资源且不触碰其他容器。

## 后续阶段

### 阶段 2：监控历史与个性化

加入历史指标、实时和历史图表、VPS 分组/搜索/排序、节点和容器别名/图标/备注/置顶，以及持久化容器排序与响应式布局。一次验收确认多节点、历史曲线、重启后偏好和手机操作正确。禁止伪造历史、错误关联容器或仅保存在前端的排序。

### 阶段 3：Docker 完整管理

完成容器完整生命周期、真实重命名/删除、日志与资源流、健康和镜像列举/拉取/删除，外部 Docker CLI 变更应同步。一次用独立容器核对生命周期和真实状态；镜像删除不得影响被容器使用的镜像。禁止第二 Client、错节点/容器操作和无用流持续运行。

### 阶段 4：Compose 与容器配置

加入 Compose 项目发现与受控操作、配置校验/编辑/保存/恢复、Compose 服务端口变更及受控重新创建、独立容器配置重建。复用统一 Core Task、Agent Runner 和共享 Docker Client，不建独立状态机。一次使用专用 Compose 项目和 `docker run` 容器验收配置变更及无效配置失败。禁止只改展示值、误删挂载或无入口功能。

### 阶段 5：终端与文件

加入主机 PTY、Docker Exec、受限文件浏览/编辑/传输。文件远程写操作复用统一任务与 Agent 日志；退出登录后连接不得继续执行。一次在测试目录验证文件读写和真实终端。路径不得越权，文件故障不得停止主机监控。

### 阶段 6：Tailscale 与 Agent 部署

发现可见 Tailnet 节点，识别 Linux VPS，提供授权 SSH 辅助安装并管理 Agent systemd 服务和连接地址。手动安装仍可用。一次对用户授权测试 VPS 验收从未安装到注册上线。禁止覆盖现有服务、引入长期 Agentless 后端或未经授权连接。

### 阶段 7：运维交付

按需要实现 HTTP/TCP 探测、告警通知、Core 备份恢复和正式安装/使用/故障文档。若实现 Agent 更新，只保留单一更新流程。一次验证服务异常、告警状态和真实数据备份恢复，再做系统集成验收。恢复后身份与数据关联必须正确，文档不得声称不存在的功能。

## 每阶段报告

阶段名称；实际修改与删除文件；唯一保留机制；真实完成的业务链路；一次必要检查及结果；尚未完成但属于后续阶段或需要用户 VPS 的事项。审查者以工作树和构建结果为准。
