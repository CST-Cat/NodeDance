# NodeDance 全功能实施与阶段验收计划

本文是项目当前执行基线，正式名称 **NodeDance**，默认端口 **127.0.0.1:8180**。它替代旧方案中的 NodeDeck 品牌和 3080 示例端口。全部功能都必须完成；P0/P1/P2 只规定顺序，不是删减范围。此文、[原始设计底稿](design-source.md)、[用户授权修订](plan-amendments.md)、[需求追踪](requirements.json)和[182项规范验收登记表](../tests/registry.json)共同构成可审阅计划。

当前代码包含 S00 基础与 S01 Core 存储、管理员认证、Session、审计和登录外观；Agent 注册及后续 S02–S17 仍未实现。正文中的命令、接口和结果是待实现契约；仅在带有本次实际运行报告且结果为 `PASS` 时，才表示该检查已通过。源码、工作流、模拟数据、截图和旧报告本身都不能代替本次实际验收。

## 1. 项目目标与范围

NodeDance 是面向单管理员的多节点 Linux 服务器与 Docker 容器统一管理平台。Core 提供 Web、鉴权、资产、历史监控、任务调度和审计；各服务器运行 Agent，负责采集、Docker 管理与实际操作；浏览器提供服务器、容器、终端、文件及 Compose 管理入口。原设计正文的功能、22 项 P0/P1/P2 需求和本文列出的增强功能都必须实现。明确排除 Kubernetes、Swarm、多租户、插件市场、完整建站、证书管理平台、AI 运维决策、云厂商控制台整合，以及 OAuth、LDAP、多用户权限系统。

项目最终应能完成从新建安装、Agent 注册、监控和外部 Docker 发现，到容器操作、Compose 修改、告警、更新、备份及恢复的完整闭环。项目交付至少包括 Core、Agent、内嵌 Web、双架构 Linux 产物、测试设施、安装与运维文档、专项设计/综合拓展/毕业设计材料。

## 2. 总体结构、版本和监听端口

采用一个 Core、多 Agent、单管理员架构。生产 Core 将前端静态资源嵌入 Go 程序；SQLite WAL 是本地持久数据存储；运行 Core 不需要安装 Node.js、Go、Docker、MySQL、PostgreSQL 或 Redis。目标节点上的 Compose 功能需要兼容的官方 `docker compose` 插件；验收使用5.4.0锁定插件，安装到仓库局部 `.tools` 并按官方SHA-256验证。Agent 主动建立到 Core 的控制连接，不新开 Agent 管理监听端口。

所有 Web、REST API、浏览器 WebSocket、Agent WebSocket 共用一个应用端口：

```text
默认监听：127.0.0.1:8180
启动：nodedance serve --listen 127.0.0.1:8180
```

允许命令行、环境变量、配置文件覆盖监听地址；解析优先级为**命令行 > 环境变量 > 配置文件 > 默认值**。默认不绑定公网网卡。端口被占用时必须报错退出，不能切换到另一个端口、不能杀死占用程序。`--dev` 只允许回环地址。安装脚本、systemd、反向代理与 Tailscale Serve 示例、测试和文档都使用 8180。Agent 主动连接，不增加另一个管理端口。

正式工具链基线：

## 3. 接口、安全与任务统一契约

所有 API 使用 `/api/v1`，所有 WebSocket 使用 `/ws/v1`。路径分区为：

| 路径 | 职责 |
|---|---|
| `/api/v1/auth/*` | 管理员登录、退出、密码与会话 |
| `/api/v1/agents/*` | Agent 注册、设备凭据、撤销 |
| `/api/v1/nodes/*` | 节点、指标、历史和设置 |
| `/api/v1/nodes/{id}/containers/*` | 容器、操作、日志和统计 |
| `/api/v1/nodes/{id}/compose/*` | Compose 项目和配置 |
| `/api/v1/nodes/{id}/images/*` | 镜像管理 |
| `/api/v1/nodes/{id}/files/*` | 文件浏览、编辑与传输 |
| `/api/v1/tasks/*` | 任务进度、日志与结果 |
| `/api/v1/probes/*` | 服务探测 |
| `/api/v1/alerts/*` | 告警、通知与历史 |
| `/api/v1/updates/*` | Agent 更新 |
| `/ws/v1/agent` | Agent 控制通信 |
| `/ws/v1/dashboard` | 浏览器实时推送 |
| `/ws/v1/streams/*` | 受控日志、终端等数据流 |

S00 只允许健康接口，不开放管理数据、API 或 WebSocket；从 S01 起，匿名接口限于初始化状态、CSRF challenge、健康状态和登录页明确公开的外观。其他管理数据、API 与浏览器 WebSocket 都必须由服务端 Session 检查。每增加入口必须补鉴权测试。浏览器 Session 与 Agent 设备凭据相互独立。WebSocket 的来源、Session、撤销和有效期必须由服务器检查。不得在 HTML、静态资源、API、缓存或日志暴露节点、IP、容器和指标。

Docker Engine 是 Docker 当前状态的唯一事实来源；别名、顺序、图标和备注属于 NodeDance 展示偏好。未知、过期和采集失败均不能写成零值。Agent 失联后容器信息必须标过期，Agent 在线与 Docker 可用分别判断。所有写操作先通过 Core 鉴权和 Agent 能力检查；同一资源的冲突写操作串行。断线后非幂等操作不得盲目重放。

所有远程写操作遵循统一任务状态：`queued`（接受并排队）、`running`（Agent 已确认开始）、`succeeded`（操作完成且实际结果已验证）、`failed`（确认失败）、`timed_out`（已确认执行终止并确认资源状态）、`canceled`（确认取消）、`unknown`（可能执行但结果未确认）。仅发送命令不能报告成功；结果不确定时展示“结果待确认”，重连后查询 Agent 记录及 Engine 实际状态。相同幂等键和请求返回相同任务，不同请求复用键返回冲突。

## 4. 统一阶段门槛和证据要求

每个阶段至少提供：源代码/提交标识、完成的需求 ID、工具链及目标版本、全部规范用例的逐项结果、真实正常/错误/恢复过程证据、更新的接口和使用文档、已知问题与影响范围。用例状态为 `PASS`、`FAIL` 或 `NOT_READY`。未执行、环境缺失、只做 Mock、只有截图或沿用旧报告均不得标 PASS。

阶段完成必须同时满足：本阶段所有原编号用例通过；真实 Core、Agent、Docker/Compose 或指定浏览器按用例需要验证；正常、失败和恢复流程均有证据；受影响的既有阶段没有回归；本阶段完整验收至少完成一次有意义的当前运行；无阻断问题、鉴权绕过、数据丢失或核心流程错误。失败或代码变更后只重跑受影响的测试套件；阶段被驳回时，修复相关模块，增加复现用例，再跑本阶段及受影响阶段；保留已正确实现的部分。

验收入口：

```sh
make check
make build
make test-stage STAGE=S00
make test-integration STAGE=S00
make test-e2e STAGE=S00
make test-stage STAGE=S01
make test-integration STAGE=S01
make test-e2e STAGE=S01
make test-acceptance
```

统一验收必须每次重新执行当前检查，不因旧报告跳过。不可实施的阶段对其全部规范用例逐条报告 `NOT_READY` 与具体缺失原因；总状态为 `NOT_READY` 且命令返回非零。工作流文件存在不等于 GitHub Actions 实际执行通过。

## 5. 分阶段实现计划

各阶段所有规范测试的操作、预期结果、环境和证据要求均以 [registry.json](../tests/registry.json) 为准。不得重编号、合并、删减，也不得用新增用例替代原182项。

### S00 项目基础、版本锁定与测试骨架（3–5 个开发日）

实施 Core、Agent、Web、共享协议边界；单一服务端口和配置解析；双架构构建；内嵌 Web；CI；需求和用例追踪；锁定 Docker/Compose fixtures、故障注入、清理入口。默认服务启动为 `nodedance` 或 `nodedance serve`，只绑定 `127.0.0.1:8180`。预期：首页直接 HTTP 200、健康 API 可用、尚未存在的管理入口拒绝访问。完成门槛是 S00-01 至 S00-08 在一次完整验收运行中全部通过、四类 Core/Agent amd64/arm64 Linux 二进制架构及 CGO 信息验证、测试仅影响唯一 NodeDance 标签和根目录。工具链偏移、浮动依赖、默认公网绑定、未内嵌 Web、CI/验收入口不能运行或环境测试会影响既有 Docker 资源时驳回。

### S01 私有 Core、管理员鉴权和审计基础（7–10 个开发日）

实现 SQLite 初始化、WAL、迁移和优雅退出；一次性本机初始化凭据；单管理员 Argon2id 随机盐密码；服务端 Session、安全 Cookie、CSRF、限流、可信代理及 WebSocket 来源检查；退出、改密、会话管理；登录页外观；敏感审计脱敏。未登录请求任意管理资源必须 `401`，没有私有数据；改密撤销旧 Session，已建立 WebSocket 也在 30 秒内失效。无凭据初始化、固定盐、明文密码、仅前端拦截、撤销后 WebSocket 永久存活、跨站请求通过或数据库迁移破坏原数据均驳回。

### S02 Agent 注册、身份与通信可靠性（7–10 个开发日）

Core 创建绑定节点、默认10分钟一次性的注册凭据；注册后分配独立设备身份，Core 仅保存长期凭据验证摘要；Agent 安全持久化凭据；实现协议版本、能力声明、5秒心跳、最多30秒失联判断、退避重连、连接代际、凭据轮换和撤销；提供注册及 systemd 安装命令。三节点身份不混用，重启后稳定复连，断网/重启后新代际同步，Agent 不新增管理监听端口。共享长期Token、日志泄露凭据、默认跳过TLS、旧代消息覆盖新状态、浏览器离线导致采集停止均驳回。

### S03 VPS 指标采集与实时展示（5–7 个开发日）

采集系统信息、架构、CPU、内存、磁盘、网卡和运行时间。CPU、内存、网络默认5秒，磁盘30秒；用计数差分计算网络速率；单项权限问题不能影响其他指标；Docker查询与采集/心跳隔离；Core无浏览器时仍收数据。公式和单位需与独立 `/proc`、文件系统观测对照。未知不能显示成0，计数器重置不能产生负速率，虚拟接口不能重复汇总，Docker卡死不能使Agent失联；正常网络指标更新P95目标不超过8秒。

### S04 Docker 全量发现、事件同步与状态模型（9–13 个开发日）

从Docker Engine全量列举所有来源（含停止容器）；使用Engine事件驱动更新并每60秒全量校验；初次连接、重连和Engine恢复执行完整快照，只有成功完整快照才可删除缺失资产；采集状态、健康、时间、网络、IP、挂载、配置端口和实际端口；处理重复/乱序/迟到事件、删除、重命名和事件历史缺口；Docker不可用时保留最后状态并标过期。外部创建、改名、停止和删除应自然同步。EXPOSE不能伪装宿主机发布；Running不能伪装应用Healthy；半份快照不能清空资产；状态与真实Engine不一致必须驳回。正常变化同步P95目标≤5秒。

### S05 持久任务、生命周期、日志和资源统计（10–14 个开发日）

Core先落库任务和审计，再下发；Agent执行前后持久化任务；幂等、互斥、超时、取消、断线待确认；真实启动、停止、重启、暂停、恢复、删除和独立容器改名；删除二次确认，默认保留卷，Compose容器拒绝真实改名；历史/实时Docker日志正确处理TTY和stdout/stderr；容器详细统计按页面订阅，退出即释放。每个操作完成后重新查询Engine验证。命令发出就报成功、盲目重放不确定操作、无限日志内存、无审计或危险操作只有前端确认均驳回。

### S06 融合首页、偏好、详情和历史监控（10–14 个开发日）

服务器与Docker融合卡片、默认4个主要容器、监控/管理视图、分组/搜索/排序/字段、别名/图标/备注/顺序/服务入口；节点和容器详情；分钟与小时历史聚合、缺失样本、加权平均、保留和清理。分钟数据默认30天，小时默认一年；别名只改NodeDance偏好，不调用Docker Rename；偏好绑定经验证的稳定身份；失联数据明显过期；服务入口必须由管理员配置。桌面/平板/手机Web响应式视口均需可读操作。身份继承错误、缺口补零、别名修改真实名称、重启后排序丢失、手机关键操作不可达均驳回。

### S07 Compose 基础管理及 P0 验收（7–10 个开发日）

发现Compose项目、服务、实例与容器；维护项目目录、配置文件顺序、环境文件和profile；支持关联已有配置；文件丢失后保留容器级管理但禁止凭空编排；实现 `up/start/stop/restart/down`；校验配置、展示真实进度并检查最终容器状态；`down` 默认保留卷、镜像及无关资源。所有13项P0和正文相关功能完成并可部署。错用项目目录、忽略环境/profile、多文件顺序、默认删卷、只看CLI零退出码报健康、P0有任何失败均驳回。

### S08 Docker 镜像管理（3–5 个开发日）

列表、搜索、标签和容器引用；真实拉取、进度、取消与验证；一次性Registry认证；检查引用并默认禁止删除使用中的镜像；接入持久任务、审计和断线待确认。假进度、失败仍报成功、默认强删引用镜像、明文保存凭据或绕过任务/审计均驳回。

### S09 主机终端与容器控制台（5–8 个开发日）

Agent侧主机PTY与容器Exec；输入输出、Unicode、终端尺寸、控制键和移动辅助键；终端会话绑定Session/节点/容器，有限并发，默认30分钟空闲关闭；Session撤销或Agent/Core断开时关闭流和PTY；只审计会话元数据，不记录敏感输入。真实主机和容器终端交互；无shell/无权限须明确失败；关闭页面、撤销授权后不能残留会话。旁路鉴权、连错目标、输入秘密写日志或响应式移动核心输入无效均驳回。

### S10 文件浏览、传输和文本编辑（7–10 个开发日）

浏览目录、属性、权限；安全创建、重命名、删除；流式上传下载（单文件默认上限1GiB）；先临时写入、校验、原子提交；编辑使用版本检查、冲突检测、备份和原子替换；校验路径根、符号链接、权限、所有者；Session撤销停止未提交传输。100MiB和1GiB文件哈希一致、增量内存差≤64MiB；失败不能损坏原文件。路径越界、失败覆盖、静默丢权限、静默覆盖SSH并行修改均驳回。

### S11 Compose 编辑与端口修改（7–10 个开发日）

源文件与结构化端口编辑；保留工作目录、多文件顺序、env/profile和相对挂载；在原上下文临时解析最终配置并展示差异、影响服务、停机影响；提交前校验文件版本并备份；固定保留旧镜像引用；仅重建受影响服务；失败恢复旧配置、镜像和服务，记录回滚失败。无效输入、文件冲突、端口占用和健康检查失败均需演练。只检查YAML语法、临时目录改变挂载、无备份、误重建无关服务或夸称业务数据已回滚均驳回。

### S12 独立容器受控重建向导（9–13 个开发日）

读取Inspect并制定保留清单；检查镜像、挂载、网络、可写层与剩余空间；必要时先快照可写层；保留旧容器并释放名字/网络后创建新实例；恢复配置、卷、网络和展示偏好；健康、端口与实际运行检查成功后完成；失败恢复旧实例；提供显式回滚资源清理，默认不删卷。容器快照不包含挂载卷内容，界面不得将其描述为业务数据备份。高风险配置不能可靠保留时，必须破坏旧容器前拒绝。先删旧容器、漏匿名卷/网络、数据卷自动删除或失败冲突均驳回。

### S13 Tailscale 发现与 SSH 辅助部署（7–10 个开发日）

读取本机 `tailscale status --json` 的可见节点；区分候选、已纳管和不适用系统；提供手动安装，或使用一次性SSH凭据启动有审计部署任务；验证主机指纹、权限、架构和发布签名；确认systemd Agent注册上线；清理失败临时文件；主路径不可用时只按显式授权启用可信HTTPS备用地址。发现节点本身不代表获得部署许可。自动发现即自动安装、忽略SSH主机指纹、长期明文凭据、默认切备用通道或再造日常SSH Docker后端均驳回。

### S14 HTTP/HTTPS/TCP 服务探测（3–5 个开发日）

由目标节点Agent发起HTTP/HTTPS/TCP探测；默认间隔30秒、超时3秒；可配目标和HTTP期望状态；默认连续3次失败异常、连续2次成功恢复；节点失联时显示未知；并发有界。回环地址从目标节点解释，TLS证书验证默认启用。浏览器代探测、忽略TLS、单次失败告警、慢探测堵塞心跳或节点离线显示探测正常均驳回。

### S15 告警、恢复与通知（6–9 个开发日）

实现节点、CPU、内存、磁盘、Docker、容器和探测告警；支持阈值、持续时间、期望运行态、去重、冷却、恢复、确认、静默和维护窗口；抑制失联节点的重复下级告警；实现站内、Webhook、SMTP通知；投递结果持久化、有界重试、凭据加密、测试发送及历史。默认资源告警可配置为90%持续5分钟。每类规则需实测触发和恢复；无限重复、未发送报成功、凭据泄漏或重启丢告警均驳回。

### S16 Agent 手动与自动更新（7–10 个开发日）

发布清单带版本、架构、校验值、协议范围和可信签名；下载暂存、容量检查、原子切换和旧版本保留；独立更新助手与开机恢复入口负责失败回滚；自动更新默认关闭，支持窗口、批次和单节点放行；活动任务/传输期间推迟；版本/连接验证失败时本地回滚；持久记录每个更新阶段；旧Agent初次升级可由安装脚本或SSH完成。无签名、覆盖旧程序无备份、唯一回滚依赖新进程、失败身份丢失或一节点失败后继续批量升级均驳回。

### S17 全量验收、备份恢复与正式发布（10–15 个开发日）

从干净环境安装Core与Agent；全量正常/负向/恢复回归；真实Linux amd64/arm64；选定Debian/Ubuntu；Docker Engine 28/29和锁定Compose；真实浏览器测试加响应式/触屏仿真；至少72小时运行；20节点/200容器容量压测，并区分真实与仿真数据；一致性备份、新机恢复和Core升级失败演练；签名发布、安装/卸载与文档；完成毕业设计材料。必须能够按“全新安装→注册→发现→管理→Compose修改→文件/终端→告警→Agent更新→Core备份恢复→Agent重连”完成真实端到端流程。

在注明配置的2 vCPU/2GiB Core、RTT≤100ms、无人为丢包环境，预算为：容器同步P95≤5秒；指标P95≤8秒；Agent失联≤30秒；任务API P95≤500ms（不含实际操作耗时）；稳态Core RSS≤512MiB；无重任务Agent RSS≤128MiB；72小时预热后资源不持续线性增长；保留策略生效后DB/WAL不无限增长。未达预算时记录并优化，不能删测试或静默放宽。缺架构实机运行、测试被跳过、仿真冒充实测、恢复丢身份/数据、文档不能安装或仍有P0/P1/P2未完成均驳回。
