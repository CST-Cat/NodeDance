# S08 implementation note

The real-Engine acceptance runner is `scripts/test/s08-image-engine-dind.sh`, launched by `.github/workflows/s08-image-engine.yml` against run-owned Engine 28 and 29 instances. It creates its own owner-marked DIND container, socket, network, and data root; it refuses an existing run directory and does not reuse or stop another stage's Engine. The local Registry image is pinned in `test-images.lock.json`; the test uploads a deterministic generated image directly to the Registry without loading it into Docker Engine first, then verifies the Registry manifest digest against Engine inspection.

The focused local run `agent-20261009g` used fresh Engine 29.7.2 on arm64. The newly created Engine's image list was empty before fixture setup. `TestDINDImageManagementRealEngine` passed once via `scripts/test/s08-image-engine-dind.sh 29 agent-20261009g`. It exercised real SDK pull, Engine Config ID and RepoDigest verification, multiple tags, stopped-container reference count, refusal to delete an in-use image, safe deletion after removing the test-owned reference and tags, missing Registry manifest failure, and invalid reference rejection. The missing-manifest task ended as `failed` with `missing_after_pull`; both SDK `Inspect` and Docker CLI `image inspect` confirmed the image was absent. Evidence is in `.artifacts/s08/image-engine29-agent-20261009g.log` and `reports/stages/S08.json`. The exact run-owned Engine and its data were cleaned with the matching marker-checked cleanup command.

The private-auth subtest now exercises a bcrypt-protected Registry against the real Agent `Executor` and SDK Engine. On a fresh owner-marked Engine 29.7.2/arm64 run (`auth-20261009c`), anonymous access returned 401, an incorrect password produced a failed task with `registry_auth_failed` and no installed image, and the valid one-use credential produced a succeeded task whose Engine ID and RepoDigest matched the seeded manifest. The test scanned both returned task JSON values and the Agent SQLite database/WAL/SHM for the username and password canaries; the runner scans its complete test output before displaying it. The focused subtest passed once. The earlier `auth-20261009b` run is retained as a failed attempt because its test helper returned a RepoDigest with the public Registry port; the helper now derives the port from the fixture URL. Both DIND runs were isolated and cleaned by their exact owner markers.

This verifies the Agent-side auth handoff, task result, Agent journal, and test-log canaries only. Core credential submission/storage/one-use delivery, Core database and audit records, Registry logs, and broader application logs were not part of this run. Engine 29.7.2 also emitted no positive SDK progress for the public fixture (`completed=0,total=0`; persisted positive-progress callback not observed), so S08-06 remains NOT_READY. The no-tag listing case in S08-01, Core/Agent heartbeat during transfer, browser UI review, and full audit/database/log evidence also remain outstanding. S08 remains `NOT_READY`.

S08-04 now has a focused real cancellation case. It seeds a 48 MiB uncompressible layer in the run-local Registry, then routes the Docker Engine pull through a static proxy inside the same owner-marked DIND namespace. The proxy limits only that blob to 2 MiB/s and reports bytes served. On fresh Engine 29.7.2/arm64 run `cancel-20261009b`, the test canceled after 2,244,608 of 50,347,195 layer bytes, observed one canceled and zero active blob requests, and verified a durable `canceled` task with `CancellationConfirmed`, `ProcessTerminated`, and `ActualResultConfirmed`. SDK inspection and Docker CLI both confirmed the image absent after the transfer stayed quiescent. The focused case passed once; evidence is `.artifacts/s08/image-engine29-cancel-20261009b.log`.

The first attempt `cancel-20261009a` is retained as failed: the helper binary was copied under `/tmp`, which the pinned DIND image mounts as tmpfs, so `docker cp` and `docker exec` saw different views and the pull never started. Moving the helper and PID file to `/var/tmp` fixed the fixture; each exact owner-marked Engine was cleaned. This verifies explicit cancellation during a real slow transfer only. A transport failure and the operation-timeout branch remain untested, so S08-04 and overall S08 remain `NOT_READY`.

The focused S08-01 subcase `dangling-20261009a` ran once against fresh owner-marked Engine 29.7.2/arm64. The test created a stopped fixture container and committed it without a repository name, producing a real untagged image. Docker CLI inspection confirmed `RepoTags` was null; SDK `Inspect` and `List` both retained the image and returned non-nil empty `Tags` and `Digests` slices with zero container references. The focused test passed and removed only its owned container and image; `scripts/test/s08-dind.sh clean 29 dangling-20261009a --purge-data` then removed only the matching owner-marked Engine, network, socket, and data root. Evidence: `.artifacts/s08/image-engine29-dangling-20261009a.log`.

A code-path review (not a runtime integration result) traced the untagged arrays through `internal/agent/image_bridge.go`: it copies Engine image fields into the protocol summary, filters by ID/tag/digest, then paginates. Protocol JSON fields are not omitted when empty; Core returns the `ImageListResponse`, and `ImagesPanel.vue` requests the filter/page with page size 50 and assigns `result.images` to component state. There is no separate image store conversion. This run did not execute the Core-Agent WebSocket, HTTP filter/pagination round trip, or browser rendering, so S08-01 and overall S08 remain `NOT_READY`.
