# S15：告警、恢复及通知

**前置阶段：** S14。  
**估算：** 6–9 个开发日。  
**候选状态：** `NOT_READY`；本机受控检查通过不等于正式阶段验收通过。

## 已实现范围

- SQLite 持久化告警规则、持续条件状态、活动/已恢复告警、事件、静默/维护窗口、通知渠道和投递队列。孤立 S15 候选使用 v6；整合分支保留 S01–S14 已应用迁移，并将告警 schema 追加为 v9。
- 规则覆盖节点失联、CPU/内存/磁盘阈值、Docker 不可用、容器状态和 S14 服务探测状态。节点失联后不再把旧指标当作当前故障，并抑制该节点活动告警的下级重复通知。离线期间重置尚未触发的持续时间，重连后必须重新累计新鲜样本。
- 首次纳管节点自动获得 CPU、内存、磁盘 **90% / 300 秒**默认规则。阈值、持续时间、冷却、级别、条件、启用状态和通知渠道均可通过受保护 API 配置。
- 告警具有去重指纹、冷却提醒、恢复事件、管理员确认、单条静默及全局/节点/规则范围的计划维护和静默窗口。确认或静默会抑制尚未开始发送的队列项；已开始的网络发送不能被追回。
- 站内活动/历史/事件视图、Webhook JSON POST、SMTP 邮件和测试发送均通过持久通知队列执行。HTTP 非 2xx 会记录响应码并有限重试；Core 重启会恢复中断的队列项。重启恰好发生在远端已接收、Core 尚未提交成功结果的窗口内时，按至少一次投递恢复，接收端可能看到重复消息。
- 渠道密钥以 AES-GCM 加密写入 SQLite；Core 数据目录中的 `alert-channel-encryption.key` 以 `0600` 保存。备份必须同时包含数据库和密钥。更换或遗失密钥会使旧密文无法解密，失败会记入投递历史，不会永久卡在队列中。
- Webhook 不跟随重定向。远程 SMTP 必须提供 STARTTLS；本机 loopback SMTP 可用于受控测试。隐式 TLS 465、真实公网 SMTP 服务商、真实 Agent 断联与恢复等场景尚未验证。
- 告警中心使用响应式布局，提供活动告警、恢复历史、事件、规则、渠道、维护窗口和投递历史页面；打开告警中心期间每 30 秒刷新，后台只读刷新不延长管理员空闲会话。浏览器自动化检查 375、768 和 1440 CSS 像素视口；这不要求或声称测试物理 iPad/Android 设备。

## 本地验收命令

```bash
make verify-tools
make frontend
make playwright-install PLAYWRIGHT_BROWSERS=chromium
make test-s15
```

`make test-s15` 一次执行聚焦 Go race suite 与 Chromium UI suite。主要本地 fixture 是真实 SQLite、Core HTTP handler、`httptest` Webhook 接收器及进程内脚本化 SMTP 接收器；Playwright 使用 API stub，只验证浏览器交互和响应式溢出，不冒充真实 Core 浏览器端到端集成。
