## 实施范围、样例和阶段门槛

从干净环境安装Core与Agent；全量正常/负向/恢复回归；真实Linux amd64/arm64；选定Debian/Ubuntu；Docker Engine 28/29和锁定Compose；真实浏览器测试加响应式/触屏仿真；至少72小时运行；20节点/200容器容量压测，并区分真实与仿真数据；一致性备份、新机恢复和Core升级失败演练；签名发布、安装/卸载与文档；完成毕业设计材料。必须能够按“全新安装→注册→发现→管理→Compose修改→文件/终端→告警→Agent更新→Core备份恢复→Agent重连”完成真实端到端流程。

在注明配置的2 vCPU/2GiB Core、RTT≤100ms、无人为丢包环境，预算为：容器同步P95≤5秒；指标P95≤8秒；Agent失联≤30秒；任务API P95≤500ms（不含实际操作耗时）；稳态Core RSS≤512MiB；无重任务Agent RSS≤128MiB；72小时预热后资源不持续线性增长；保留策略生效后DB/WAL不无限增长。未达预算时记录并优化，不能删测试或静默放宽。缺架构实机运行、测试被跳过、仿真冒充实测、恢复丢身份/数据、文档不能安装或仍有P0/P1/P2未完成均驳回。

#### 本地 Core/Agent 恢复候选

`make test-integration STAGE=S17` 通过 `scripts/acceptance-s17.py` 只运行一次 `TestS17BackupRestoreRealCoreAgentReconnect`，并将完整 frontend setup 与 Go 测试输出保存在报告所引用的候选日志中。该用例使用真实 HTTPS Core handler、真实注册 Agent runtime 和临时 SQLite 数据目录：HTTPS Core API 用于创建 Agent enrollment、保存和读取 dashboard 设置/节点偏好/指标历史/通知渠道；Agent 通过真实 WSS runtime 上报指标并在恢复后重连。停服后的备份和新目录恢复直接调用生产 Go 函数 `corebackup.Create` 与 `corebackup.Restore`，并非 HTTP 备份/恢复端点。测试停止源 Core 后将备份写到 dataDir 外，恢复至全新的临时 dataDir，重启 Core，并验证通知秘密可由恢复密钥解密后发送到测试自建的 loopback receiver。备份、源目录、恢复目录、Agent 凭据和测试接收器全部受测试生命周期管理。

该候选成功也只提供同一主机上的本地恢复闭环证据，不等同于独立新主机恢复、发布升级或完整 S17 验收；本地候选日志、Node/Agent ID、备份和密钥文件摘要记录在 `reports/stages/S17.json`。因此该项及整体 `S17` 仍为 `NOT_READY`，直到独立恢复主机及其余规范用例完成。

候选第一次实际运行因测试 SQL 错把 `node_id` 读自 credential verifier 而失败；按真实 schema 改为联接 `agent_devices` 后聚焦闭环通过一次。两次完整日志均保留在 `.artifacts/logs/acceptance-s17/`，报告保留该失败与修正后结果。
