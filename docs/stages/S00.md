## 实施范围、样例和阶段门槛

实施 Core、Agent、Web、共享协议边界；单一服务端口和配置解析；双架构构建；内嵌 Web；CI；需求和用例追踪；锁定 Docker/Compose fixtures、故障注入、清理入口。默认服务启动为 `nodedance` 或 `nodedance serve`，只绑定 `127.0.0.1:8180`。预期：首页直接 HTTP 200、健康 API 可用、尚未存在的管理入口拒绝访问。完成门槛是 S00-01 至 S00-08 在一次完整验收运行中全部通过、四类 Core/Agent amd64/arm64 Linux 二进制架构及 CGO 信息验证、测试仅影响唯一 NodeDance 标签和根目录。工具链偏移、浮动依赖、默认公网绑定、未内嵌 Web、CI/验收入口不能运行或环境测试会影响既有 Docker 资源时驳回。

## 实施步骤

1. 建立 `cmd/nodedance`、`cmd/nodedance-agent`、`internal/core`、`internal/protocol` 和 `web` 边界。Core 负责 HTTP/WebSocket 服务与配置，Agent 负责后续节点侧工作，共享协议包不能反向依赖 Core 或 Web，Web 只包含浏览器资源。
2. 锁定 Go 1.26.8、Node.js 22.23.3、pnpm 12.10.1、Go/frontend依赖与测试镜像。工具下载到忽略跟踪的 `.tools/`；pnpm 使用仓库内 npm lock 和启用的 lifecycle 安装相同版本 native ELF，校验 npm integrity、二进制 SHA-256 和无 Node PATH 直接执行；Compose 使用本地 Docker CLI config、官方 v5.4.0 release checksums 和 amd64/arm64 SHA-256。不得改系统默认工具或用户 Docker 配置。
3. 实现服务监听地址解析：命令行参数覆盖 `NODEDANCE_LISTEN`，再覆盖配置文件，最后采用 `127.0.0.1:8180`。默认启动 `nodedance` 与显式启动 `nodedance serve` 等价；`--dev` 只接受 loopback。Web、API、同端口 WebSocket 共用唯一 listener。端口冲突必须带错误退出；成功绑定之前不输出“listening”。
4. 从 Web 源码构建静态文件并嵌入 Core 二进制。正式 Core 启动不需要安装 Node.js；生产入口返回首页必须直接 `200`，不通过 FileServer 造成 `/` 和 `/index.html` 的重定向循环。S00基线的未实现管理 API/WS 曾返回404；S01建立统一私有入口鉴权后，未登录访问必须返回401且没有私有数据，Agent WS 仍保持未实现并拒绝连接。
5. 为 Core 和 Agent 统一设置 `CGO_ENABLED=0`，生成宿主、Linux amd64、Linux arm64 产物。用 ELF 架构头及 Go build metadata 证明产物架构和 CGO 设置，不以编译命令退出码代替检查。
6. 建立 `make bootstrap/check/build/test-stage/test-integration/test-e2e/test-acceptance`，结构化原始182项需求用例追踪及逐项机器报告；只有当前实际执行的新报告能影响本阶段状态，后续未开发阶段必须逐项 `NOT_READY`。CI 固定 GitHub Actions SHA，配置 `ubuntu-24.04` 和 `ubuntu-24.04-arm` × Engine 28/29 矩阵。workflow 文件存在不等于远端 Actions 已通过。
7. 建立 `test-images.lock.json`、独立 DIND socket、仅挂载仓库 `.artifacts/fixtures` 的数据根及 owner marker。普通/Compose fixture使用唯一运行ID与精确资源标签，具有外部生命周期变更、健康故障、日志、端口、数据卷标记；故障测试仅停止 NodeDance 自有 DIND 容器。清理必须核对 owner marker，仅删除当前 run label；比较宿主非套件容器的名称、ID、状态清理前后相等。

## 运行样例

```bash
make bootstrap
make check
make build
.build/nodedance
curl -i http://127.0.0.1:8180/
curl -i http://127.0.0.1:8180/api/v1/health
```

期望首页和健康检查是直接 HTTP `200`，没有 `Location` 重定向；未登录访问 `/api/v1/nodes` 与 `/ws/v1/agent` 返回 `401`，响应不含私有数据。默认只监听 loopback。把端口环境变量设为 `127.0.0.1:18180` 后，Web 和 API 都必须从 18180 提供；将监听参数设为 `0.0.0.0:8180` 并使用 `--dev` 必须报错。将独立 sentinel 占住 8180 时，Core 非零退出、没有成功监听日志、sentinel 仍用原标记响应。

S00-08 的 Docker fixture另包含真实 `nd-log` 容器：分别向 stdout、stderr 写入 `你好` UTF-8 标记。验收检查容器 TTY 为关闭、Docker 使用 `json-file` 驱动，并读取隔离 daemon 中实际的原始 JSON log file，校验每个记录的 `stream` 字段和 Unicode 内容；再确认 `docker logs` 能读出两类文本。测试报告会记录实测 Docker CLI、宿主 Engine、DIND Engine、Compose 版本、选中插件路径和摘要。
