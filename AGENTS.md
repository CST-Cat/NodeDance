# NodeDance repository rules

- Treat the current product behavior as the only implementation. Do not add compatibility branches, adapters, migrations, or tests solely for retired modes, APIs, or behavior. Remove deprecated duplicate code and documentation when it is in scope.
- Agent enrollment, recovery, runtime, file service, and systemd service are root-only. Do not generate or support a non-root restricted Agent or file-service mode.
- Agent releases use the `agent-vMAJOR.MINOR.PATCH` tag namespace (for example, `agent-v0.1.0`). Only those tags trigger the Agent release workflow; Core release tags use a separate namespace. Generated installer commands default to the latest stable published Agent at execution time and must not hardcode a tag. Resolve only the Agent release namespace; do not use a repository-wide `latest` release URL.
- Preserve current security requirements: Agent credentials must remain owner-protected in a `0700` state directory and `0600` regular config file; file management must reject traversal, symlinks, Agent credential paths, and protected kernel/runtime trees.
- Tailscale is an optional network capability. NodeDance may detect it and expose the existing Agent installation entry when available. Agent installation remains root-only. NodeDance does not install or configure Tailscale or change its configuration.
- Work directly on `main`; do not create branches.
- The project is in development. Do not increment product versions, release tags, or capability version names unless the user explicitly authorizes a version increment. Extend the current implementation without adding retired-contract compatibility branches.
- CLI and TUI are two presentations of the same terminal product and must expose identical management and local maintenance capabilities, including all valid inputs, submission, observation, cancellation, retry and recovery. They must share operation definitions and execution/workflow code; invoking the other interface is not capability coverage. Keep both downstream of the Core API and discovered operation contract.
- Web must expose shared remote management capabilities and may add graphical interactions and browser-local view operations. Any graphical operation that changes shared configuration, permissions, tasks or remote resources must use a Core operation also accessible from CLI and TUI. Presentation differences must not create separate business validation, permissions, confirmations or execution semantics. A capability change is incomplete until applicable interfaces, documentation and behavior verification are updated.
- The connected Core publishes the single operation contract at `/api/v1/operations`. Web, CLI, and TUI must discover operations, request schemas, methods, routes, and transports from that contract. New Core capabilities must appear automatically in their generic operation interfaces; specialized screens are presentation only. Do not maintain independent client operation lists or duplicate business validation.

## Web UI rules

- All new, replaced, or refactored Web UI components MUST be local components installed through the shadcn CLI. This includes UIArc, the configured `@uiarc` registry at `https://uiarc.dev/r/{name}.json` in `web/components.json`. Reuse installed sources in `web/src/components/ui/` and `web/src/components/arc/`; consult `web/uiarc-manifest.json` before installing missing components. Do not hand-build replacement controls, copy pasted component implementations, or introduce another UI library.
- Preserve installed component styles and behavior. Only map colors to the project's existing theme tokens and bind business data/Core operations. Do not redesign component internals, override radii globally, add competing hover/focus backgrounds, or stretch internal icon controls with generic button rules. Layout CSS may arrange sections, rows, external widths and alignment. Dropdown Menu retains its default modal blocking, focus, keyboard and transition rules.
- Follow the current user preferences in `DESIGN.md`: compact Codex desktop settings layout, left labels/right controls on narrow screens, aligned control widths, native component radii, black/white interaction highlights, and no blue UI accents. Related rounded groups and restrained separators are allowed; parameter card matrices and unnecessary secondary copy are not. Avoid unnecessary secondary labels and descriptions. Let the layout do the explaining. Do not add code comments.
- Do not use capsule/pill UI, including green, red or other colored status badges. Render status as plain text without a border or background; do not use Badge or hand-built pill replacements. Preserve installed control geometry rather than globally changing radius tokens.
- Across Docker details, Compose projects, service probes, images, container rebuild, historical monitoring, event history, node settings, domain certificates, node enrollment, alerts, host management, updates, subscriptions, operations, overview, global overview and personal settings, preserve installed Card frames and Separator dividers. Row height follows actual content plus the original vertical padding: middle rows have 8px above and below, the first row has only 8px below, and the last row has only 8px above. Thus a row containing a 44px control is 60px in the middle and 52px at either edge, excluding dividers. A single-row group has neither top nor bottom row padding. Do not force the whole row to 44px or remove its breathing room. Shared SettingsGroup cards use 8px top and bottom padding (py-2) at the usage layer, preserving installed Card frames and dividers without changing the base Card globally. Card padding is separate from the 52/60/52px row heights; do not use py-0 and leave edge controls touching the frame. Remove redundant page-level vertical margins within these groups and omit empty internal field labels rather than compensating by shrinking rows. Keep labels with content and externally associated accessible names. Let multiline content and compound records grow without clipping. Preserve installed radii, horizontal padding, control dimensions, normal section spacing and the purposeful boundaries of professional tables, charts, file management and resource cards.
- User instructions and the current component/preference rules take precedence over visual references. Use Hallmark for design skill work. The user-selected Figma reference is `https://www.figma.com/community/file/1597641111449594397/mcp-apps-for-claude`; `Caho1/open-claude-ui` is supplementary. Do not claim to have read Figma components or variables without retrieving them. Specialized Web presentation does not create separate business behavior.
- Verify actual visible controls and their interaction states, not only wrapper geometry. Assert that expected elements exist before evaluating collections. Maintain selectors when screens change. Distinguish functional assertions, geometry checks, screenshot capture, manual visual review, touch/device checks and deployment verification; do not present combination counts or unrelated test passes as proof of visual quality. Browser audits must use freshly built embedded Web assets.

- Keep tests minimal and behavior-focused. Do not add broad page/theme/width/language Cartesian matrices, screenshot galleries, duplicate audits, or assertions that merely repeat CSS constants. Browser suites do not generate screenshots by default; create only a targeted image when the user explicitly requests one or a specific unresolved defect requires it. Run the smallest applicable checks, preserve security/data-integrity regressions, and remove obsolete selectors and redundant cases when changing the relevant tests.

## Required behavior verification

- Preserve and maintain the real-browser guest regression and adversarial scripts (`web/scripts/audit-guest.cjs` and `web/scripts/guest-attacks.cjs`). Changes to guest behavior, authentication/session handling, public data projection, resource removal/revocation, or the Core operation contract must update applicable cases and documentation (`docs/guest-display.md` and `docs/guest-security.md`) and pass the guest browser security suite against freshly built Web assets. `pnpm --dir web audit:guest-security` is a convenience entry; equivalent direct Node.js execution is valid, and the testing requirement does not mandate a package manager. Discover operation coverage from the connected Core contract; do not freeze operation/case counts or weaken assertions to hide failures. Fix reproduced problems and retain regression cases for them.
- Guest tests must continue to verify default opt-in, identical public data with administrator cookies, valid administrator sessions when returning to management, direct anonymous API boundaries, forged identities, method/path/query bypasses, WebSocket denial, CSRF, stored script injection, bounded concurrent refresh, and immediate publication withdrawal after policy changes, deletion, revocation or disable. Use an isolated real Core, temporary data and a protocol-only simulated Agent; never target production or real remote control resources. Keep the test scripts and documentation; generated screenshots, snapshots, databases and binaries may be removed after verification.

- Maintain `web/scripts/audit-files.cjs` for file-manager changes. Build fresh Web assets and verify isolated real Core/root Agent file fixtures, actual installed shadcn file dialogs, pagination/search, mutation recovery, edit conflicts, passive preview boundaries and light/dark/mobile layouts. Do not target production filesystem, remote resources or Docker controls. Keep file-manager license notices in sync with locked dependencies (`node web/scripts/file-notices.cjs --check`).

- Update eligibility uses only stable component tags. Never block an update by comparing protocol, capability, API, manifest format or storage fingerprints. Preserve artifact checksums, architecture selection, authentication, request identity, runtime health checks and failure recovery.
- Updates are built into Core and Agent. Keep default `nodedance update` and `nodedance agent update` usable without update-specific setup or extra arguments. Do not introduce separate updater binaries, release assets, installer scripts or persistent update services. Use the same product binary for any transient work needed to survive restart.
- The latest Core release must point to the newest stable published Agent release. When paired installer changes require both releases, publish Agent before Core; verify the pairing before Core publication.
- Every release tag must rehearse before it is created. Before pushing an `agent-v*` or `core-v*` tag, run `python3 scripts/release-rehearsal.py run <component> <tag>` (Core additionally passes `--agent-tag`); the rehearsal validates tag format, reviewed bilingual changelog, exact Agent pairing, newest-stable-pairing and that the tag/release does not exist, without creating anything. Only a passing rehearsal allows tagging: both release workflows refuse to publish a tag without a recorded passing rehearsal. If a rehearsal fails, stop, fix the cause and rehearse again; never push the tag to "test" the release workflow.
- After completing implementation changes and passing the applicable checks, directly deploy the verified working-tree build to production at `https://nd.2023989.xyz`. This is the user's standing authorization and preferred delivery workflow; do not ask for production-sync confirmation again or substitute a devweb preview. Do not increment product versions or create release tags.
- Use the standard Makefile production deployment flow: `make build` (always builds Web assets before the Go binaries; never hand-run `pnpm build`/`go build` separately, since an out-of-order pair embeds stale assets), then `sudo make install`, then `sudo systemctl restart nodedance.service`. For style/copy-only changes, use focused browser/visual verification instead of full regression suites; behavior or contract changes must pass the applicable regression suites before deployment. Never touch the production data directory (`/var/lib/nodedance`) or edit the unit file. Afterwards verify `systemctl is-active nodedance.service`, the local health endpoint on 8180, and that the served JS/CSS assets match the verified build and contain the change. Confirm the public entry `https://nd.2023989.xyz` (Cloudflare tunnel via `nodedance-tunnel.service`) serves the same new assets. Report deployment and verification accurately.
- Devweb is optional and only used when explicitly requested. Do not build, restart or maintain it as a default development delivery step. If requested, it remains isolated at `https://devweb.2023989.xyz` (local 8181, data `/var/lib/nodedance-devweb`); never share production credentials into it, and immediately consume bootstrap credentials after any initialization so no public setup window remains open.

- Documentation-only changes require a document/diff check, not a Web rebuild, preview restart or production deployment.
